AIMP Launcher — the local API trusts the null CORS origin

A drive-by web page can read the local machine's drives and directories through the launcher's loopback API while it is running.

Component: AIMP.Launcher Class: CORS misconfiguration (CWE-942 / CWE-346) Vector: Drive-by browser, no auth Status: Confirmed, fix available

Summary

The AIMP Launcher runs a local HTTP API (default http://127.0.0.1:5127) that browses the filesystem and controls the game (validate / launch / inject / shutdown). Access is meant to be limited to the AIMP frontend by a CORS origin allow-list (IsLocalFrontendOrigin in Program.cs). That allow-list unconditionally trusted the opaque null origin:

if (string.Equals(origin, "null", StringComparison.OrdinalIgnoreCase)) return true;

Browsers send Origin: null from sandboxed <iframe> elements and data: URLs. Any web page a user visits can create such a context, so while the launcher is running, an arbitrary website can read responses from the local API — a classic drive-by exposure of a localhost service.

Root cause

CORS is supposed to be the gate that keeps other web origins from reading this API. The gate special-cased the string "null" and returned allowed. But null is not a trustworthy identity — it is the opaque origin shared by:

  • sandboxed iframes (<iframe sandbox="allow-scripts">),
  • data: documents,
  • some cross-origin redirect chains.

An attacker's page can deliberately put its own request into a null-origin context, so "allow null" effectively means "allow anyone who asks."

Why the browser normally blocks this

When a page on https://attacker.example runs fetch("http://127.0.0.1:5127/…"), the browser sends the request (sending to loopback is allowed) but then checks CORS before letting the page read the response. Normally the launcher would not return an Access-Control-Allow-Origin matching the attacker, so the browser discards the body and the attacker learns nothing.

The bug defeats that: the launcher answers Access-Control-Allow-Origin: null, and a page can make its own origin null via a sandboxed iframe — so the browser hands the response back.

Attack scenario

The attacker never touches the victim's machine directly. The API is loopback-only and cannot be reached from the network. Instead the attacker makes the victim's own browser be the bridge: 127.0.0.1 in the victim's browser is the victim's machine.

Requirements for the attacker: (1) the launcher is running, and (2) the victim loads attacker-controlled JavaScript in a browser (a malicious link, a malvertising iframe, or an XSS/compromised site). No local code execution, no control of the victim's IP, and no takeover of any AIMP domain is required.

Evidence

1. The server explicitly blesses the null origin (and the private-network bypass)

Replaying the browser's preflight with curl:

$ curl -i -X OPTIONS http://127.0.0.1:5127/api/v1/filesystem/drives \
     -H "Origin: null" \
     -H "Access-Control-Request-Method: GET" \
     -H "Access-Control-Request-Private-Network: true"

HTTP/1.1 204 No Content
Server: Kestrel
Access-Control-Allow-Methods: GET
Access-Control-Allow-Origin: null                 <-- trusts the opaque origin
Vary: Origin
Access-Control-Allow-Private-Network: true        <-- green-lights public -> local

By contrast, a genuine remote origin is correctly refused (no Access-Control-Allow-Origin header is returned):

$ curl -i http://127.0.0.1:5127/api/v1/filesystem/drives -H "Origin: https://evil.example"
HTTP/1.1 200 OK
(no Access-Control-Allow-Origin)

2. A sandboxed, cross-origin page reads the local drives in a real browser

A page served from a different origin, running its request inside a sandbox="allow-scripts" iframe (origin null), successfully read the machine's drive list in Google Chrome:

 {"id":"D:\\","name":"860 evo","path":"D:\\","type":"FIXED", ...},

Drive labels, types and byte counts are returned verbatim. The same technique applies to …/filesystem/directory?path=C:\Users\<name> to walk folders.

Private Network Access nuance

Modern Chromium has a Private Network Access (PNA) protection that gates requests from a public site to a private address such as 127.0.0.1. This affects exploitability but does not make the launcher safe:

  • When the request's initiator is itself local (e.g. the demo served from 127.0.0.1:8080), PNA does not apply and the read succeeds outright.
  • For a truly public attacker page, Chromium issues a PNA preflight — which the launcher answers with Access-Control-Allow-Private-Network: true for the null origin (see Evidence #1), i.e. it actively permits the bypass.
  • Enforcement varies by browser and version. Firefox does not implement PNA the same way, and older Chromium builds do not block it at all.

A browser-side safeguard is not a substitute for the server not trusting null in the first place.

Impact & severity

Confidentiality: an untrusted web page can enumerate drives and directory contents on the victim's machine and exfiltrate them — no authentication, no user interaction beyond visiting a page.

Integrity/availability: state-changing endpoints (launch, inject, shutdown) are also reachable cross-origin; impact varies as some require a valid game directory, but they should never be callable from an arbitrary web origin.

Preconditions that bound the risk: the launcher must be running, and the victim must load the attacker's JavaScript in a browser whose PNA policy allows the request.

Reproduction

  1. Start the launcher so the API listens on 127.0.0.1:5127.
  2. Serve a proof-of-concept page from any other origin, e.g. python -m http.server 8080.
  3. Open the page in a browser and let it run a fetch to /api/v1/filesystem/drives from inside a sandbox="allow-scripts" iframe.
  4. Vulnerable build: the drive listing is returned to the page. Fixed build: the browser blocks the cross-origin read.

A read-only PoC that never calls any state-changing endpoint is sufficient to demonstrate the issue.

The fix

Stop trusting null by default. Accept only concrete local origins (loopback, the file:/app: schemes, or one named by AIMP_FRONTEND_ORIGIN). A packaged frontend whose engine reports Origin: null can opt back in explicitly with an environment variable that is off unless deliberately set.

-    private static bool IsLocalFrontendOrigin(string origin)
+    internal static bool IsLocalFrontendOrigin(string origin)
     {
-        if (string.Equals(origin, "null", StringComparison.OrdinalIgnoreCase)) return true;
+        // The opaque "null" origin is NOT trusted by default. Browsers send
+        // Origin: null from sandboxed iframes, data: URLs and some redirect
+        // chains, so any web page could otherwise reach this loopback API while
+        // the launcher is running (a drive-by / CSRF read of the local machine).
+        if (string.Equals(origin, "null", StringComparison.OrdinalIgnoreCase))
+            return AllowsNullOrigin();
         if (!Uri.TryCreate(origin, UriKind.Absolute, out var uri)) return false;
         if (uri.IsLoopback
             || string.Equals(uri.Scheme, "file", StringComparison.OrdinalIgnoreCase)
             || string.Equals(uri.Scheme, "app", StringComparison.OrdinalIgnoreCase))
             return true;
         /* …AIMP_FRONTEND_ORIGIN match unchanged… */
     }
+
+    private static bool AllowsNullOrigin()
+    {
+        var value = Environment.GetEnvironmentVariable("AIMP_ALLOW_NULL_ORIGIN")?.Trim();
+        return string.Equals(value, "1", StringComparison.Ordinal)
+            || string.Equals(value, "true", StringComparison.OrdinalIgnoreCase);
+    }

A regression test (CorsOriginTests) asserts the gate accepts legitimate local origins, rejects null and remote origins by default, and honors the opt-in.

Remediation guidance

  • Default-deny null (the fix above).
  • Frontend compatibility: if the UI loads over file:// and relied on the old behavior, migrate it to the already-whitelisted app: custom scheme, which yields a stable, non-opaque origin — rather than leaving the null allowance on.
  • Stronger follow-up (optional): for a localhost service the most robust defense is a shared launch token — the launcher mints a random secret at startup, passes it to the frontend it spawns, and requires it on every request. That removes reliance on the Origin header entirely. It touches the separate frontend repo and is out of scope for the CORS fix.

Disclosure

This issue was identified during a source review, reproduced against a running launcher with a read-only proof of concept, and reported to the project maintainer together with the fix above. The proof of concept was limited to read-only endpoints and exfiltrated no data.
